## 1. How to use this document

**Scope assumed by this document:**

This document assumes scope B: Engage (the voice pick system) stays in place and `order_picking` becomes a planning layer behind it. The plan is produced as files that a person can load or read. It does not replace voice, send tasks to headsets, or take confirmations.

- If the owner chooses scope A (LoadMax only), do step A0 and stop. Record the decision in `DECISIONS.md`.
- If the owner chooses scope C (replace voice), steps A0 to A8 still apply. A separate design is needed for task push, confirmation, exceptions, and labor data. It is not in this document.

**Protocol for every step:**

1. Read `AGENTS.md`, `DECISIONS.md`, and `order_picking/TRIED.md` first. A closed try in `TRIED.md` is not repeated unless the input or the rule changed.
2. Work on one step per chat and one branch. Do not mix steps.
3. Every new behavior is optional. With the new columns, files, and flags absent, every output must equal the baseline captured in step A0.
4. Read the "Files to read first" list of the step before editing. Use find-usages on every function whose signature you change.
5. After editing Python, run `python -m py_compile <files>`. Run `ruff` or `mypy` on the same files if they are on PATH. Run `python -m pytest order_picking` from the repository root.
6. Do not run the full 16-truck `chunk_model.py` solve (about 475 s) unless the step changes cover logic. Use one or two trucks first.
7. Update the README sections named in the step. Add a dated block to `DECISIONS.md` and a row to `TRIED.md` only after the user confirms a finding.
8. Stop at the acceptance criteria. Do not start the next step.
9. If something important is unknown, stop and ask. Do not guess business numbers.

**Prompt to give the agent for one step:**

## 2. Glossary

| Term | Meaning | Confidence |
|---|---|---|
| Engage | The voice pick system used by Maersk TH outbound. The leader opens it to check data from SAP and enters pickers into it. | Stated in the deck |
| DDL | A document run by Data Outbound that reserves products against the truck plan and produces a group number and a DDL number. Exact meaning not given in the deck. | Name only |
| Group number | Produced when the DDL is run. Used here as the grouping key when no truck exists. | Name only |
| Checking list | Printed product checking list, with the loading dock set by the outbound leader. | Stated |
| Bulk picking | Whole-pallet picking done with an RT. | Stated |
| Pick-face (case picking) | Case picking done with a PPT. | Stated |
| RT | Most likely a reach truck (high-rack pallet truck). Not spelled out in the deck. | Inference, confirm |
| PPT | Most likely a powered pallet truck (low-level electric pallet truck). Not spelled out in the deck. | Inference, confirm |
| Staging area | Outbound area where picked pallets wait before loading. No capacity given. | Stated, no number |
| Pallet changer machine | Machine the wrapped pallets are moved to before loading. | Stated |
| LoadMax | This repository's truck loader (`loadmax/`). In the deck it runs after picking. | Stated |
| Job | One carryable trip: a set of pick lines one picker does in one walk from the depot and back. Stored as an `order_id` in `orders.csv`. | Repository |
| Depot / dock | `depot_id`, for example `PACK_A`. The place a picker starts and returns to. | Repository |

The names RT and PPT are never used as equipment type strings in the code. Equipment types stay `pallet_jack` and `forklift` (or whatever a site file uses). Modes are separate (section 6).

## 3. Source evidence

**Sources:**

| Source | What it gives |
|---|---|
| `Maersk Outbound CON FG WH TH process.pptx` (3 slides, text only; the 24 images are small icons) | Current Thai outbound flow, and where LoadMax is added |
| Email "Fw: LoadMax for outbound" (Narisara Chinpumiwasana, 2025-01-29) | Two options for where LoadMax sits, and the voice cost case |
| Lucas "Voice Picking Software Selection Guide" PDF | Generic voice-pick facts and pricing. Not Kenvue-specific |
| Arvato / Gurobi webinar slides (images in `order_picking/webinar notes/`) | Allocation and batching ideas, triaged in `order_picking/webinar notes/not_adopted.md` |

**Facts stated by the sources:**

- F1. Picking runs in Engage. The outbound leader opens Engage to check data from SAP and defines the loading dock in the checking list and in Engage.
- F2. Data Outbound enters picker names into Engage separated into Bulk Picking and Pick-face.
- F3. Bulk picking uses an RT. Case picking uses a PPT. Pickers move goods to the outbound staging area.
- F4. Before picking, Data Outbound compares system quantity with the DDL and the truck plan, reserves products, runs the DDL, receives a group number and DDL number, prints the product checking list, and the CL admin emails the order confirmation.
- F5. After picking: the checker inspects material, batch, and quantity; pallets are wrapped, moved by RT to the pallet changer machine, staged, and loaded by PPT or by the supplier; Data Outbound checks the TO and prints the invoice.
- F6. In the LoadMax version, stock is picked to the staging area first. LoadMax then calculates the number of trucks per route and suggests which orders go on each truck, using master data. The supplier loads following LoadMax.
- F7. Email option 1: LoadMax first (consolidated order, LoadMax assigns truck and picking priority, replaces Voice Pick). Option 2: LoadMax last (transport team consolidates orders, runs LoadMax by route design, LoadMax says which SKU is at the bottom). Voice costs about 157 USD per user per month, with 10 users in TH and 8 in MY. Replacing it would save at least 2 warehouse staff per location.
- F8. Lucas guide: voice alone gives 5 to 10% productivity; with optimization 20 to 90%. Full-pallet-only sites see little voice benefit. Voice systems capture task data for labor management and provide exceptions (out of stock, damage), skip, and help.

**Inferences (not stated, confirm with the business):**

- I1. Bulk and pick-face run in the same wave.
- I2. RT means reach truck and PPT means powered pallet truck.
- I3. One SKU can exist in a bulk location and a pick-face location.
- I4. The RT drivers who pick may also move wrapped pallets.
- I5. Slide 3 implies LoadMax may run before any truck exists. Slide 1 says "Plan truck" happens before picking. The two readings conflict.

No weight capacity, pallet capacity, staging capacity, pick share, or step time is given in any source. All such numbers in this document are illustrative and must be replaced from data.

## 5. Gaps and the step that closes each

| Gap | Why it matters | Step |
|---|---|---|
| G1. No bulk / pick-face distinction | Wrong crew gets the work; capacities and times are wrong (F2, F3) | A1, A2 |
| G2. One set of caps and times for every job | A pallet move and a case-pick tour are different work | A2 |
| G3. Jobs require a truck | The planner may run when no truck exists yet (I5) | A3 |
| G4. One location per line, no batch, no stock check | Real stock sits in several places and batches (I3, F5) | A4 |
| G5. Staging has no capacity | A plan can meet deadlines and still overfill the floor (F3, F5) | A5 |
| G6. Flat 30 min buffer, no checker or wrap steps | Downstream steps can miss departure (F5) | A6 |
| G7. Crew counted per dock, no other duties | Capacity is overstated (I4) | A7 |
| G8. Output is CSV and HTML only | A leader must enter pickers into Engage by hand (F2) | A8 |
| G9. No import from DDL / SAP | Input is synthetic (F4) | B1 |

## 6. Design

**Principles:**

1. Extend, do not replace. The weighted and staged assignment, the savings chunker, and the set-partitioning chunker stay.
2. A blank column means "any". Existing CSVs keep working and produce identical output.
3. Rules and reports before models. Allocation, staging, and downstream checks start as deterministic rules and reports. A MIP is added only if a measurement on real data shows the rule is poor. This follows the closed-try practice in `TRIED.md`.
4. New numbers come from CSV files, never from code constants.
5. Output columns that only exist for new features are written only when the feature is used, so baseline files do not change.
6. LoadMax is not coupled to the picker in this document.

**Target flow (scope B):**

```mermaid
flowchart LR
    DDL["DDL / SAP export (B1)"] --> ALLOC["Allocation rule (A4)"]
    STOCK["Stock by location and batch"] --> ALLOC
    ALLOC --> CHUNK["Chunker with pick modes (A1, A2, A3)"]
    PROFILE["Mode profile (A2)"] --> CHUNK
    CHUNK --> ASSIGN["Assignment (existing staged solve)"]
    CREW["Crew policy (A7)"] --> ASSIGN
    ASSIGN --> STAGING["Staging check (A5)"]
    ASSIGN --> DOWN["Downstream check (A6)"]
    ASSIGN --> SHEET["Picker task sheet (A8)"]
    SHEET --> ENGAGE["Leader enters or imports into Engage"]
```

**Pick mode values:**

`pick_mode` is a free lowercase string. The Maersk values are `bulk` and `pickface`. A blank means any mode. A job never holds two different non-blank modes. A blank-mode line may join a job of either mode.

**New and changed inputs:**

| `stock.csv`, `sku_master.csv` (new) | Allocation inputs | Only for A4 |

### A1. Pick mode and mode-aware eligibility

**Gate:** none. Mode names are free strings.

**Goal:** a job has a pick mode. A picker has allowed modes. A job goes only to a picker that allows its mode.

**Files to read first:** `order_picking_optimizer.py` (`_eligible`, `_picker_blockers`, `_is_missing`, `_field`), `assignment_reports.py` (`drop_detail`), `chunk_loads.py` (`_Line`, `_read_lines`, `_within_caps`, `_pack_in_order`, `_savings_routes`, `_job_record`, `_frames`), `chunk_model.py` (`PickerSpec`, `read_pickers`, `_picker_fits`, `failure_reason`, `required_equipment`, `_order_atoms`, `_bundle_ok`, `_reject_infeasible`, `_selected_job`).

**Changes (picker side):**

1. In `order_picking_optimizer.py` add `_mode_set(value) -> Optional[frozenset]`. It returns `None` for a missing or blank value. Otherwise it splits on `;`, strips, lowercases, and drops empty parts.
2. Add `_mode_allows(order_row, picker_row) -> bool`. It reads `pick_mode` from the job and `allowed_modes` from the picker with `getattr`. It returns `True` when either is `None`.
3. `_eligible` returns `False` when `_mode_allows` is `False`. Keep the current checks unchanged.
4. `_picker_blockers` returns `pick_mode` for a picker blocked only by mode. Keep `equipment` and `capacity` as they are.
5. `drop_detail`: `kinds == {"pick_mode"}` returns `pick_mode`. Any other set that contains `pick_mode` returns `pick_mode_and_other`. Existing branches do not change.
6. Do not change any function signature in `solve_order_assignment`. The new columns arrive through the DataFrames.

**Changes (chunker side):**

1. `ORDER_COLUMNS` and `ITEM_COLUMNS` do not change. `_frames` appends a `pick_mode` column to `orders.csv`, `order_items.csv`, and `jobs.csv` only when at least one line has a non-blank mode.
2. `_Line` gets `pick_mode: str = ""` as its last field. `_read_lines` reads and normalizes it (strip, lowercase, blank if missing).
3. Add `_modes_compatible(lines) -> bool` in `chunk_loads.py`. It is `False` when two different non-blank modes appear. Call it first in `_within_caps`. Because `_pack_in_order` and the savings merge use `_within_caps`, no merge can mix modes.
4. `_job_record` stores `pick_mode`: the one non-blank mode, or blank.
5. In `chunk_model.py`, `PickerSpec` gets `allowed_modes: Optional[frozenset] = None`. `read_pickers` reads the optional `allowed_modes` column with the same parsing as step 1 of the picker side.
6. `_picker_fits`, `failure_reason`, and `required_equipment` get an optional `mode: str = ""` argument. A picker whose `allowed_modes` is set and does not contain a non-blank `mode` does not fit. Update every call site (use find-usages): `_reject_infeasible` (two calls), `_jack_tier_blocks` and `_line_above_jack` (pass the line or job mode), `_bundle_ok`, and `_selected_job`.
7. `_bundle_ok` returns `False` for a bundle with incompatible modes.
8. `_order_atoms`: group lines by `(source order, mode)` instead of source order. A source order with lines of two modes becomes two atoms. Record this rule in the README: a mixed-mode order is split by mode because bulk and pick-face are different tasks.
9. `failure_reason` adds the reason `no_picker_for_mode` when the line or order fits a picker on weight and volume but no picker allows its mode. Such rows go to `rejected.csv`.
10. `_selected_job` sets `required_equipment` only from pickers that allow the job's mode.

**Tests (add to the existing files):**

- Optimizer: a `bulk` job is not eligible for a `pickface`-only picker; a blank-mode job is eligible for all; a blank `allowed_modes` allows everything; `drop_detail` returns `pick_mode`.
- Chunker (both): two lines of different modes never share a job; a mixed-mode source order becomes two jobs in the cover model; with no mode columns the outputs equal the A0 baseline; `no_picker_for_mode` appears in `rejected.csv`.

**Acceptance:** A0 test passes; new tests pass; `order_picking/README.md` and `chunker/README.md` list the new columns.

**Do not:** rename `pallet_jack` or `forklift`; make `pick_mode` mandatory; use RT or PPT as code constants.

### A2. Mode profile (per-mode caps and times)

**Gate:** A1 done. Values are illustrative until B2.

**Goal:** bulk and pick-face jobs use their own caps, line limits, pick times, and overhead.

**Files to read first:** `chunk_loads.py` (`ChunkSettings`, `_within_caps`, `_pack_in_order`, `_savings_routes`, `_job_record`, `_frames`, `main`), `chunk_model.py` (`ChunkModelSettings`, `_parse_settings`, `_cw_settings`, `_bundle_ok`, `_candidate_cost`, `main`).

**Changes:**

1. New file `order_picking/chunker/mode_profile.py` with a frozen dataclass `ModeCaps` and `read_mode_profile(path: Path) -> Dict[str, ModeCaps]`.
2. `mode_profile.csv` columns: `pick_mode, max_job_lines, max_job_weight, max_job_volume, default_pick_time, job_overhead, pallet_basis`. A blank cell means use the global value. `pallet_basis` is `job` (a job is one pallet, the default) or `line` (each line is one pallet).
3. Validate: unique `pick_mode`, numbers finite and non-negative, `max_job_lines` at least 1, `pallet_basis` in `{job, line}`. Errors name the file, row, and column.
4. Add `mode_caps: Mapping[str, ModeCaps]` (default empty, `field(default_factory=dict)`) to `ChunkSettings` and `ChunkModelSettings`. Add `--mode-profile PATH` to both `main` functions.
5. Add a helper on the settings, `caps_for(mode) -> tuple` returning the effective `max_job_lines`, `max_job_weight`, `max_job_volume`, `default_pick_time`, and `job_overhead`. A mode not in the profile, or a blank mode, uses the global values.
6. Replace every read of `settings.max_job_weight`, `max_job_volume`, `max_job_lines`, `default_pick_time`, and `job_overhead` with the mode-aware value. Find them with `grep` on `settings.max_job` and `settings.default_pick_time` and `settings.job_overhead`. In the cover model, `_cw_settings` and `_parse_settings` must carry `mode_caps` through. `_candidate_cost` uses the bundle's mode.
7. `_frames` writes the mode's `default_pick_time` for a line with no `pick_time`.
8. When a profile is given, `jobs.csv` gets a `pallets` column: 1 for `pallet_basis = job`, the line count for `line`. Without a profile there is no `pallets` column.
9. The per-mode weight and volume caps are limits on top of the picker limits. A job must satisfy both.

**Example file (illustrative only; the README must say so):**

```text
pick_mode,max_job_lines,max_job_weight,max_job_volume,default_pick_time,job_overhead,pallet_basis
bulk,1,,,0.5,2,line
pickface,15,,,0.5,5,job
```

**Tests:** with no profile, output equals A0; with `bulk` `max_job_lines=1` every bulk job has one line; per-mode `default_pick_time` appears in `order_items.csv`; per-mode overhead changes `_candidate_cost`; `pallets` appears only with a profile.

**Acceptance:** as A1, plus a README table for `mode_profile.csv`.

**Do not:** ship guessed values as defaults; change the heaviest-picker rule or the `--jack-tier-merges` default.

### A3. Wave input without a truck

**Gate:** none. It is additive. The business answer (I5) decides whether it is used.

**Goal:** the chunkers accept a load table grouped by a group or DDL number, with a wave cutoff instead of a truck departure.

**Files to read first:** `chunk_loads.py` (`_REQUIRED_LOAD_COLUMNS`, `_read_lines`, `_job_record`, `_derived_base`, `main`), `chunk_model.py` (`_order_keys`, `_parse_settings`, `main`).

**Changes:**

1. `_read_lines` accepts `group_id` when `truck_id` is absent or blank on a row. The grouping key is stored in `_Line.truck_id`, so every downstream output keeps the `truck_id` column name. If both columns exist, `truck_id` wins. Update the missing-column check to require `truck_id` or `group_id`.

5. Read `_order_keys` in `chunk_model.py` before editing. It must not depend on `truck_id` being a column of the raw table.

**Tests:** a table with `group_id` and no `departure_time` runs through both chunkers; with `--wave-cutoff 120` every job has cutoff 120; a table with neither `truck_id` nor `group_id` raises a clear error; existing truck tables are unchanged.

**Acceptance:** as A1.

### A4. Stock locations and the allocation rule

**Gate:** none for the rule. Real stock data is needed only to calibrate it (B3).

**Goal:** turn demand lines (SKU, quantity) into pick lines with real stock locations, bulk first and pick-face for the remainder. It is a pre-step. The solver does not read stock files.

**Files to read first:** `order_picking/inputs/layout_warehouse/wh_inventory.csv`, `wh_skus.csv`, `locations.csv`, `order_picking/webinar notes/not_adopted.md`, `chunker/build_truck_loads.py` (for the output shape).

**New file:** `order_picking/chunker/allocate_lines.py` (argparse CLI, `pathlib`).

**Inputs:**

- `demand.csv`: `truck_id` or `group_id`, `depot_id`, `destination_id` (optional), `sku_id`, `quantity`, `must_ship` (optional), `account_tier` (optional), `departure_time` (optional).
- `stock.csv`: `sku_id, location_id, batch_id, pallet_id, qty, expiry, location_type`. `location_type` is `bulk` or `pickface`. `expiry` is optional.
- `sku_master.csv`: `sku_id, unit_weight_kg, unit_volume_m3, case_qty, pallet_qty`. A blank `case_qty` means 1. A blank `pallet_qty` means there is no pallet tier.
- `--travel` (the travel-time CSV) and `--depot`, for the nearest-location tie-break. Use `_build_lookup` from `order_picking_optimizer.py`.

**Rule (deterministic):**

Process demand lines in order of `departure_time` (blank last), `must_ship` first, then input order. Stock is consumed as lines are processed. For each line, `remaining = quantity`:

1. Pallet tier: while `pallet_qty` is set and `remaining >= pallet_qty`, take a whole pallet row from `bulk` stock whose `qty >= pallet_qty`. Emit a line with mode `bulk`, quantity equal to the pallet quantity.
2. Case tier: `cases = floor(remaining / case_qty)`. Take whole cases from `pickface` rows first, then from `bulk` rows. Emit lines with the mode of the row's `location_type`.
3. Residual tier: the remaining units below one case. Use an already-opened case (tracked per `(location_id, batch_id)`) if it holds enough. Otherwise open a case from the `pickface` row with the smallest `qty` that covers it. Emit a `pickface` line.
4. Within each tier, order candidate rows by earliest `expiry` (blank last), then shortest `depot -> location` travel time, then `location_id`.
5. Reduce the row's available `qty` by what is taken. Never take more than a row holds.
6. If stock is short, write the shortfall to `short_stock.csv` (`sku_id, requested, allocated, short`) and exit non-zero unless `--allow-short` is given.

**Output:** a load-table-shaped CSV: `truck_id, depot_id, destination_id, departure_time, source_order_id, item_id, sku_id, location_id, quantity, weight, volume, pick_time, must_ship, account_tier, pick_mode, batch_id, pallet_id`. `weight = quantity * unit_weight_kg` and `volume = quantity * unit_volume_m3`. A missing SKU in `sku_master.csv` is written to `allocation_rejected.csv`, and the run exits non-zero. Do not guess a weight.

**Report (printed and written to `allocation_summary.csv`):** full-pallet rate, full-case rate, opened-case count, and total depot-to-location walking minutes. Add the numbers to `TRIED.md` only after the user confirms. If the numbers show the rule is poor on real data, reopen the Allocation row in `not_adopted.md` (its condition, one SKU in more than one pallet or case, is then met).

**Tests (new `order_picking/tests/test_allocate_lines.py`):** single-location SKU gives the same line as today; whole pallet first; then cases; residual opens the smallest covering case; earliest expiry wins; stock is not oversold across two demand lines; short stock exits non-zero; missing SKU master rejects.

**Acceptance:** the output runs through `chunk_loads.py` and `chunk_model.py` unchanged.

**Do not:** read `wh_inventory.csv` inside the solver; build a MIP; change `not_adopted.md` without the measurement.

### A6. Downstream lead times and a queue check

**Gate:** none for the code. The times come from B2 or the business.

**Goal:** replace the flat 30-minute buffer with step times, and test whether a downstream step (checker, wrapping, pallet changer, loading) misses departure.

**Files to read first:** `assignment_reports.py` (`schedule_lateness`, `staging_peaks`), `run_docks.py`, `chunk_loads.py` (`staging_buffer`).

**Changes:**

1. New optional `lead_times.csv`: `step, order, fixed_minutes, minutes_per_pallet, resource_count`. `order` is the sequence (1, 2, ...). A blank `resource_count` means 1.

It reads a schedule (job id, finish minute, deadline minute) plus pallets per job, and simulates FIFO queues: each job enters step 1 at its finish minute, waits for a free server, takes `fixed_minutes + minutes_per_pallet * pallets`, then enters step 2, and so on. **Tests:** one server and two jobs finishing together shows queue delay; two servers removes it; no file gives the current output.
