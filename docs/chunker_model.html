Truck load chunker model

One wave of customer orders is packed onto trucks, each truck is split into picker jobs, and the picker then routes and assigns those jobs. This page is that whole path, with the set-partitioning chunker in order_picking/chunker/chunk_model.py as the middle step. The picker math is order_picking_model.html.

End to end

The sample path is three programs, in order. Each one writes files the next one reads. Stock placement is optional and sits in front of the chunker. Pallet loading is a separate model, loadmax_model.html, and these files are not its input.

StepProgramWhat it does
Optional. Stock chunker/allocate_lines.py Places demand onto stock before the chunker when a stock file is supplied. A whole pallet stays its own line. Cases that share order, truck, SKU, location, batch, and mode become one line, and a leftover at that same key joins it. Each output line pays one walk from the depot to that location. The 16-truck sample is already a truck-load file and skips this step.
1. Truck loads chunker/build_truck_loads.py Keeps each source order on one truck. Fills trucks to about 8–12 tonnes. Odd trucks use PACK_A and even trucks use PACK_B. Writes inputs/chunk_warehouse/truck_loads.csv.
2. Chunk chunker/chunk_model.py Splits one truck at one dock into jobs a single picker can carry. HiGHS chooses which jobs to use. The picker is chosen in step 3.
2, alternative chunker/chunk_loads.py Run this instead of the model for a fast Clarke–Wright split. A fitting order can land on more than one job. With --pickers, the cap is the heaviest machine.
3. Pick source/order_picking_optimizer.py One dock at a time. Phase 1 builds each job's walk from that dock. Phase 2 gives each released job to one picker, and the job stays whole. source/run_docks.py runs every depot folder and then sums busy minutes against the shift.

The sample wave is 16 trucks, 300 source orders, and 2,295 lines. Each order sits on one truck, one dock, and one stop, and has at most 12 lines. Run the commands from order_picking/. Use one of the two chunkers, then run the picker once for each dock. 

python chunker/build_truck_loads.py
python chunker/chunk_model.py --loads inputs/chunk_warehouse/truck_loads.csv --travel inputs/layout_warehouse/travel_times.csv --pickers inputs/layout_warehouse/pickers.csv --out outputs/chunk_model
python chunker/chunk_loads.py --loads inputs/chunk_warehouse/truck_loads.csv --travel inputs/layout_warehouse/travel_times.csv --pickers inputs/layout_warehouse/pickers.csv --out outputs/chunk_loads
python source/order_picking_optimizer.py --orders outputs/chunk_model/by_depot/PACK_A/orders.csv --items outputs/chunk_model/by_depot/PACK_A/order_items.csv --pickers inputs/layout_warehouse/pickers.csv --travel inputs/layout_warehouse/travel_times.csv --depot PACK_A
python source/run_docks.py --by-depot outputs/chunk_model/by_depot --pickers inputs/layout_warehouse/pickers.csv --travel inputs/layout_warehouse/travel_times.csv --out outputs/chunk_assign/docks --lateness-weight 1 --time-limit 60

The model prices each candidate with a Held–Karp tour and stores that length in walk_minutes. The 5 minutes per job and the pick time are in the objective and in solve.csv, and they stay out of walk_minutes. The line order written for a chosen job is nearest neighbor from the dock, so that sequence can differ from the tour that set walk_minutes. The savings command stores its nearest-neighbor tour in walk_minutes.

Phase 1 computes a new walk from the dock and the job's slots. The default tour is nearest neighbor plus directed 2-opt. --phase1 highs asks for an exact tour. Phase 2 then assigns each released job to one eligible picker. A job that the shift cannot hold, or that loses to a higher-weight set of jobs, stays unreleased. The default assignment maximises release weight. The stop is a tenth of the smallest positive weight, raised above solver noise when that still sits below half a job. A caller relative gap is ignored. --lateness-weight charges minutes past cutoff_time, read as minutes from the start of the shift, with each picker working in earliest-deadline order. --prefer-jack charges a jack-eligible job given to a forklift. Both default to 0. On --staged-assignment any positive --prefer-jack minimises that count with coefficient 1. The 16-truck result is under Open decisions. --staged-assignment releases must-ship jobs by count, then the other jobs by weight, then minimises lateness. The weighted sum stays the default. The chunker's 5 minutes are a batching charge, and the picker leaves them out of the walk. run_docks.py solves each depot folder and then raises if one picker's summed busy minutes exceed the minutes left on shift_duration. A pass is that minute total. Clock overlap and the walk between docks stay outside the screen. A named home_depot keeps that picker on one dock. A blank home, and a picker file with no home column, still enters every dock. The picker math is order_picking_model.html.

On 2026-10-21 that dock command, with lateness weight 1 and a 60 second stage limit, released every job on both docks under the weighted objective and again under --staged-assignment: 84 of 84 at PACK_A and 87 of 87 at PACK_B, late minutes 0, every stage proven. The five PACK_B jobs left out by an earlier relative gap, TRK02-J02, TRK14-J09, TRK14-J15, TRK16-J01, and TRK16-J03, are in both plans. The reports are outputs/chunk_assign/gap_wave/.

What the chunker decides

A truck carries many order lines. A picker can only carry so much on one trip. The chunker decides which lines go together in each trip.

GoalSplit each truck's lines into one-trip picker jobs.
Cost of a jobWalking minutes + 5 min per job + each line's pick time (0.5 min when the file leaves it blank).
ScoreTotal minutes over all jobs of the truck. Lower is better.
SolverHiGHS, through scipy.optimize.milp. One model per truck and dock.

The pick time is the same for every split (every line is picked once), so it never changes which split wins. It stays in the cost so that a job's minutes read like a real picker duration. The Clarke–Wright chunker in chunk_loads.py stays as the quick standalone option.

The commands are in End to end. solve.csv minutes is the full objective: the Held–Karp walks, plus 5 minutes per job, plus the pick times. The sum of walk_minutes is the walking part alone.

The crew

MachineCountWeight limitVolume limit
Pallet jack82500 kg2.0 m³
Forklift45000 kg4.0 m³

A job holds at most 15 lines (--max-job-lines). Weight and volume are judged together on one picker. On this crew the forklift holds both the highest limits, so a job fits when it is within 5000 kg and 4.0 m³. A job only a forklift can carry is marked required_equipment = forklift. A job a pallet jack can carry leaves that field blank, so either machine may take it. Each picker has a 480 minute shift. The chunker leaves the shift to the picker.

The rules

Whole ordersA customer order that fits one picker stays in one job. Several orders can share a job.
Stops can mixOrders for different stops at the same dock can share a job. --destination-grouping keeps one stop per job.
Too bigAn order no single picker can carry goes to rejected.csv. It is not split to force a job.
Must-shipMust-ship lines carry a flat priority weight of 100000 on their job. That weight is not in the minutes objective.
One modeBulk and pick-face stay in different jobs. The cover rejects an order one mode at a time, so one mode can leave while the other stays.
Mode capsA filled line, weight, or volume cap is the smaller of the mode value and the global value. Pick time and job overhead take the mode value when the profile sets them.

A must-ship line rides only in a priority-eligible job. By default that is any feasible job containing it; --priority-max-lines is an optional tighter cap. An ordinary job gets its base weight times the line count, divided by 10. This sample has no base-weight column and a blank account tier, and every truck leaves inside the 8-hour wave, so that base is 4 and the weight is 0.4 times the line count. The picker keeps the written weight as the release coefficient. The chunker minutes leave it out. Cutoff is the truck departure minus 30 minutes, in minutes from the wave start. Because the job already has a priority weight, the picker keeps that weight.

The idea in one picture

List many possible jobs, price each one, then pick the cheapest set that covers every line exactly once.

Price of a job = shortest closed walk from the dock through its distinct pick slots and back (Held–Karp), plus 5 minutes, plus each line's pick time.

The model

This is a set partitioning model: choose jobs so every line lands in exactly one chosen job.

SymbolMeaning
\(K_t\)Candidate jobs for truck \(t\) at one dock
\(z_k\)1 if job \(k\) is used, else 0
\(a_{lk}\)1 if line \(l\) is in job \(k\)
\(U_k\)Distinct pick slots of job \(k\) (a shared bin is visited once)
\(c_k\)Minutes of job \(k\)
\[ c_k = \mathrm{HK}(\text{dock}, U_k) + \theta + \sum_{l \in k} \pi_l \] \[ \begin{aligned} \min \quad & \sum_{k \in K_t} c_k z_k \\ \text{s.t.} \quad & \sum_{k} a_{lk} z_k = 1 && \text{every line, exactly once} \\ & \sum_{k \in K_t^{priority}(l)} a_{lk} z_k = 1 && \text{every must-ship line, by a priority-eligible job} \\ & \sum_k z_k \le m_t && \text{optional job-count cap} \\ & z_k \in \{0,1\} \end{aligned} \]

\(\theta\) is 5 minutes per job, or that mode’s overhead when the profile sets one. \(\pi_l\) is the line's own pick time, or 0.5 minutes when the file leaves it blank, or the mode’s pick time when the profile sets one and the line is blank. Under an exact cover the pick times add up to the same total for every split, so they do not change which cover wins. Weight, volume, and the 15-line limit are applied when a job is built, so a job that breaks them is never a row. A mode profile uses the smaller of its cap and that global cap. Its pick time and overhead replace the global values in \(c_k\) when the profile sets them. A truck with two docks gets two models, because each walk starts and ends at its own dock.

Building candidate jobs

  1. Singletons. Every whole order that fits is a job on its own (or a single line, when there is no order id). This guarantees a cover always exists.
  2. Enumeration. By default, every union of whole orders at the dock that still fits the line cap, the location cap and one picker. A union that already fails is not grown further, so the list stays far below \(2^n\).
  3. Savings candidates. With --destination-grouping, a stop with at most 10 orders (max_enumerate_lines) is fully enumerated; a larger stop gets its singletons plus the Clarke–Wright merges. Clarke–Wright jobs are kept in the pool so the model is never worse than the heuristic.
  4. 16-location cap. Held–Karp handles up to 16 pick slots plus the dock. A job with more is not built. With 15 lines per job, a job has at most 15 slots, so this cap removes nothing extra today.

Time limit and fallback

HiGHS gets 120 seconds per truck and dock (after pricing). If it has a cover when time runs out, that cover is kept and solve.csv records the mip_gap; 0 means proved best. If it has no cover, that truck uses the line-level savings jobs, which can split an order: fallback is true and mip_gap is blank. minutes is that truck's full objective.

Where the time goes

Almost all of the time is the walking tour of each candidate, in Python, before HiGHS starts. Truck 1 has 1,301 candidates. Building that list takes under 0.01 s. The 1,270 merged jobs are different sets of locations, so the tour cache, which already stores a tour by dock and sorted slots, hits only the 31 single orders. A lower bound equal to the sum of each stop's cheapest outgoing leg dropped none of those merged jobs.

Open decisions

  • Keeping an order whole. The rule stays. On this wave it costs at least 604 minutes against a savings run that may split orders. The note for the owner is order_picking/chunker/order_whole_cost_memo.md. Splitting only the large orders has not been measured.
  • Pallet jack for a light job. --prefer-jack defaults to 0. On --staged-assignment any positive value minimises the count of jack-eligible jobs given to a forklift. The 2026-10-21 run kept every release and zero lateness, proved that count at 0, and then booked PJ04 and PJ08 past a shared 480-minute shift. The default stays 0. Reports are outputs/chunk_assign/gap_wave/staged_prefer_jack/.
  • One crew for both docks. A named home_depot keeps that picker on one dock. A blank home still enters every dock, so those people are counted twice. run_docks.py sums busy minutes against shift_duration. That sum caught PJ04 at 506.5 and PJ08 at 504.7 on the prefer-jack plan. A total that still fits can overlap on the clock, and the 1.1-minute walk is outside the sum. A roaming crew on one clock is still open.
